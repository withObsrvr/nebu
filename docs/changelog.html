Changelog

Notable changes to nebu, per release.

Full release artifacts — binaries, container images, checksums — live on GitHub Releases.

v0.7.10

latest
GitHub release →
  • The documentation checks read their ledgers once from the archive, and finish again. The default RPC endpoint now refuses the third getLedgers call in a burst, so a suite where twenty-odd checks each fetched their own ledgers could not complete however long it waited. Sixteen checks whose subject is a query rather than an RPC command now read from files fetched once from the public archive; the whole suite runs in about half a minute and asks RPC for four fetches. The four checks that document an RPC command keep using one, because moving those would have made the suite pass while no longer checking what it claims to.
  • The published processors and this site agree on the nebu version again. A processor's _nebu_version names the nebu it was built against, so the samples here moved to v0.7.9 once the registry rebuilt onto it — which is also the bump that made a one-ledger processor run about four times faster on a cold fetch.
  • The samples show three fields token-transfer gained: the asset type, an operation index that distinguishes absent from zero, and the CAP-67 destination metadata. The last is worth reading carefully — it is usually the transaction memo rather than a muxed account id, and it is empty on most events.

v0.7.9

GitHub release →
  • A one-ledger RPC read downloaded ten ledgers. The Stellar SDK's RPC backend asks for ten ledgers per request by default and nebu never said otherwise, so --start-ledger N --end-ledger N fetched 11.9 MB of base64 metadata to use 1.0 MB of it — and that download was two of the run's two and a half seconds. The request is now sized to the range whenever the range is smaller. A single-ledger run goes from about 1.8s to about 0.8s; longer ranges are deliberately untouched, because a bigger buffer means fewer round trips.
  • The same decision existed twice. nebu fetch builds its own stream rather than going through the shared source package, so it kept the old behaviour after that package was fixed: still ten ledgers for one, 2.6s. Now 1.4s. Decoding a ledger and emitting its 601 token transfer events takes 26 ms — the work was never the slow part.
  • Archive mode is measured against RPC, and the ten seconds it costs off EC2 is named. A one-ledger fetch from the public pubnet archive takes 10.8s by default and 0.7s with AWS_EC2_METADATA_DISABLED=true: deciding whether to use anonymous credentials means walking the credential chain, whose last stop is the EC2 metadata service, and nowhere near EC2 that probe runs until its retries expire. With it set, 100 ledgers take 4.5s from the archive against 27.2s over RPC.

v0.7.8

GitHub release →
  • This documentation site is redesigned. All eight pages were rewritten against a smaller shared stylesheet, for a net 2,063 fewer lines, with the version moved from a per-page footer line into the header and the site footer. The documented-sample checks pass against the new markup unchanged, so every sample on these pages is still parsed out of the page and compared against what a processor actually emits.
  • The published processors and the CLI report the same nebu again. A processor's _nebu_version names the nebu it was built against, not the CLI that installed it, so after the registry rebuilt onto v0.7.7 the samples on this site moved with it. Until that rebuild an event reading v0.7.5 beside a CLI reading v0.7.7 looked like a stale install and was not one.
  • One close-time renderer, thirteen copies retired. Ten processors each carried a verbatim copy of the same RFC 3339 millisecond formatter, with the same comment explaining the same reason not to use time.RFC3339Nano; three more wrote the layout out again by hand, one of them spelled differently. They all call processor.FormatCloseTimeRFC3339 now, and the output is byte-identical either side of the change.
