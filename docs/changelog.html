Changelog

Notable changes to nebu, per release.

Full release artifacts — binaries, container images, checksums — live on GitHub Releases.

v0.7.8

latest
GitHub release →
  • This documentation site is redesigned. All eight pages were rewritten against a smaller shared stylesheet, for a net 2,063 fewer lines, with the version moved from a per-page footer line into the header and the site footer. The documented-sample checks pass against the new markup unchanged, so every sample on these pages is still parsed out of the page and compared against what a processor actually emits.
  • The published processors and the CLI report the same nebu again. A processor's _nebu_version names the nebu it was built against, not the CLI that installed it, so after the registry rebuilt onto v0.7.7 the samples on this site moved with it. Until that rebuild an event reading v0.7.5 beside a CLI reading v0.7.7 looked like a stale install and was not one.
  • One close-time renderer, thirteen copies retired. Ten processors each carried a verbatim copy of the same RFC 3339 millisecond formatter, with the same comment explaining the same reason not to use time.RFC3339Nano; three more wrote the layout out again by hand, one of them spelled differently. They all call processor.FormatCloseTimeRFC3339 now, and the output is byte-identical either side of the change.

v0.7.7

GitHub release →
  • One way to render a close time. processor.LedgerCloseTimeRFC3339 and processor.FormatCloseTimeRFC3339 give the RFC 3339 UTC millisecond form that DATA-3 asks events to carry. Reading the value was already shared; rendering it had been solved three separate times, and time.RFC3339Nano — the obvious answer — drops trailing zeros, so a ledger closing on a whole second renders with no fractional part and the field's shape varies with its value. These render three digits always.
  • The Protocol 30 review is accepted for nebu and the registry, and measured against ledgers that now exist: testnet voted on 2026-11-03. Over 400 consecutive testnet ledgers the millisecond close time reads correctly, every ledger is the signed-with-milliseconds arm, and there are no same-second pairs yet — so CAP-88's ambiguity is permitted but not observable, and the empty-transaction-set arm still has no real ledger to test against, exactly as the review predicted from the code side.
  • Measuring that adoption found a defect counting it would have missed. Twelve of the registry's fourteen origin processors read the shared helper and none still call the truncating SDK accessors — but token-transfer's millisecond field was derived from a truncated value, because the Stellar SDK's own token transfer processor builds its event meta from a whole-second close time. On one Protocol 30 ledger it reported ...44.000Z where the ledger closed at ...44.916. Fixed in the registry the same day.

v0.7.6

GitHub release →
  • A new example reads ledger entries out of a history archive checkpoint. checkpoint-entries streams a full state snapshot as JSONL, which is the nebu shape of the Stellar ingest SDK's “Ledger Entry Statistics” example: that one prints four totals, this one emits the entries those totals are counted from, so the statistics are a query and a fifth question needs no second read. The other two SDK examples already had nebu equivalents, in both library and processor form, and examples/README.md now maps all three.
  • It reads the hot archive too — the bucket list holding entries state archival has evicted, which nothing in nebu touched before and no SDK example covers. The gap is not small: on one testnet checkpoint there are 9,403,519 archived contract data entries against 1,001,740 live ones, so “how many contract data entries exist” has two answers nine times apart depending on which list you read. Every event says which list it came from.
  • A checkpoint read that fails exits 8 and says to discard what it wrote. Each bucket's hash is checked only after its entries have been read, so a failure invalidates everything, not just the tail — and a run stopped at a limit is not verified at all, which it now reports rather than leaving to the SDK's documentation. A ledger that is not a checkpoint is refused before any fetch, naming the two nearest.
  • The registry pin check could report a stale pin as current. It asked the module proxy's latest-version endpoint, which caches: after the registry's main moved, the proxy kept answering with the previous commit, so the check whose only job is noticing that said everything was fine. It asks the registry's git HEAD now, and its advice includes the priming step a repin needs — the proxy does not index a nested module until something asks for it by path, and without that go install resolves the parent module and fails.
