Changelog

Notable changes to nebu, per release.

Full release artifacts — binaries, container images, checksums — live on GitHub Releases.

v0.8.0

latest
GitHub release →
  • nebu fetch streams through pkg/source instead of building its own. pkg/source gained a raw-ledger interface, RawLedgerSource, so a consumer that wants the bytes rather than a decoded ledger no longer has to reach for the SDK itself. Direct ledger-stream construction outside pkg/source went from four sites to zero, and the build now fails on a new one. The duplication had already cost a real bug: a fix for over-fetching landed in pkg/source/rpc and never reached nebu fetch, so a one-ledger read kept downloading ten. Output is unchanged, checked byte for byte from both the archive and RPC.
  • pkg/source/rpc, pkg/source/storage and pkg/runtime joined the stable surface. Their constructors and entry points are committed; the defaults and tuning inside them are deliberately not, so a repair like the over-fetch fix stays possible. The policy had promised a permanent LedgerSource interface while listing the only documented way to obtain one as an explicit non-commitment.
  • NEBU_REGISTRY_TOKEN authenticates the community-registry lookup, falling back to GITHUB_TOKEN and GH_TOKEN. Without one, GitHub caps the API at 60 requests per hour per IP, and past that nebu list quietly showed only the built-in processors.
  • Security: a reachable standard-library vulnerability is fixed, along with every open dependency advisory that has a patch. go.work had pinned an older Go toolchain than go.mod, and in workspace mode it wins — so every local build used the vulnerable compiler while CI, which installs from go.mod and never downgrades, stayed green. govulncheck now reports none reachable.

v0.7.11

GitHub release →
  • go-stellar-sdk v0.9.0, and the millisecond close time is read by the SDK now. v0.9.0 added the same five-arm walk over the ledger close time that nebu wrote during the Protocol 30 work, so nebu delegates rather than keeping a second copy. Output does not move: the same pubnet ledger yields identical statistics either side of the upgrade, and a Protocol 30 testnet ledger still reports its millisecond close time exactly.
  • That delegation fixed a panic. Reading the value by hand went through a generated accessor that dereferences the union arm, so a millisecond arm with no value crashed the run — and a crash inside a processor's per-ledger method ends a run that is supposed to carry on past bad data. No ledger from the network reaches it; a hand-built one does, which is exactly what the Protocol 30 review says to construct for the empty-transaction-set case the network has not produced yet.
  • The archive and RPC disagree on byte order, not content. The same ledger from both sources has identical transaction, operation, diagnostic-event and change counts, and differs only in the order ledger entry changes are emitted within an operation: 30 of 169 transactions, 81 operations, and every one of those 81 holding the same set of changes. Compare decoded output rather than file hashes, and read the archive-mode guide for the separate case where a source is configured to emit less.

v0.7.10

GitHub release →
  • The documentation checks read their ledgers once from the archive, and finish again. The default RPC endpoint now refuses the third getLedgers call in a burst, so a suite where twenty-odd checks each fetched their own ledgers could not complete however long it waited. Sixteen checks whose subject is a query rather than an RPC command now read from files fetched once from the public archive; the whole suite runs in about half a minute and asks RPC for four fetches. The four checks that document an RPC command keep using one, because moving those would have made the suite pass while no longer checking what it claims to.
  • The published processors and this site agree on the nebu version again. A processor's _nebu_version names the nebu it was built against, so the samples here moved to v0.7.9 once the registry rebuilt onto it — which is also the bump that made a one-ledger processor run about four times faster on a cold fetch.
  • The samples show three fields token-transfer gained: the asset type, an operation index that distinguishes absent from zero, and the CAP-67 destination metadata. The last is worth reading carefully — it is usually the transaction memo rather than a muxed account id, and it is empty on most events.

v0.7.9

GitHub release →
  • A one-ledger RPC read downloaded ten ledgers. The Stellar SDK's RPC backend asks for ten ledgers per request by default and nebu never said otherwise, so --start-ledger N --end-ledger N fetched 11.9 MB of base64 metadata to use 1.0 MB of it — and that download was two of the run's two and a half seconds. The request is now sized to the range whenever the range is smaller. A single-ledger run goes from about 1.8s to about 0.8s; longer ranges are deliberately untouched, because a bigger buffer means fewer round trips.
  • The same decision existed twice. nebu fetch builds its own stream rather than going through the shared source package, so it kept the old behaviour after that package was fixed: still ten ledgers for one, 2.6s. Now 1.4s. Decoding a ledger and emitting its 601 token transfer events takes 26 ms — the work was never the slow part.
  • Archive mode is measured against RPC, and the ten seconds it costs off EC2 is named. A one-ledger fetch from the public pubnet archive takes 10.8s by default and 0.7s with AWS_EC2_METADATA_DISABLED=true: deciding whether to use anonymous credentials means walking the credential chain, whose last stop is the EC2 metadata service, and nowhere near EC2 that probe runs until its retries expire. With it set, 100 ledgers take 4.5s from the archive against 27.2s over RPC.
