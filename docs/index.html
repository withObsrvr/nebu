Stellar indexer toolkit

Make Stellar data composable

Small programs. Powerful pipelines.

Pull data out of Stellar with standalone processors, then pipe it into the tools you already use. Build indexers, analytics, and automations with Unix pipes. You don't need a proprietary pipeline engine.

A Unix pipeline 
token-transfer --start-ledger 60200000 --end-ledger 60200100 \
  | jq -c 'select(.transfer.assetCode == "USDC")'

token-transfer is a nebu processor. jq is plain jq. The pipe between them is the only integration they need.

Stellar data in. Your tools out.

Stellar provides the ledger data. nebu makes it easier to work with. It packages Stellar's RPC access, XDR, and ingest SDK into standalone processors that read ledgers and write newline-delimited JSON.

Each processor does one thing. You can chain processors with pipes, put jq or DuckDB between them, or write your own. Go authors build on nebu's stable interfaces, and any other language works if it follows the processor contract.

Your pipeline. Your tools. Processors read stdin and write stdout. That lets them run alongside other processors, Unix utilities, and programs written in any language. nebu doesn't own anything on the far side of the pipe.

Two ledger sources, one contract. Use --mode rpc for live tailing and recent ranges. Use --mode archive to read deep history from a GCS or S3 ledger archive without RPC rate limits. Either way you get the same XDR, the same processors, and the same JSON.

You don't need a daemon, a pipeline file, or a managed service. Processors are ordinary executables, and you decide how to run them. Start with a pipe. Add infrastructure only when you need it.

Designed for composition

Compose with anything

Processors talk through standard streams. Use them with jq, DuckDB, shell scripts, or your own programs. There's no custom pipeline engine to learn.

Read Stellar data your way

Stream recent ledgers over RPC, or read history from GCS and S3 ledger archives. The same processors run on either source.

Build and share processors

Write origins, transforms, and sinks against the stable pkg/processor contract, which CI checks against committed API snapshots. Ship each one as its own binary and list it in the community registry.

Discoverable by developers and agents

Every processor answers --describe-json with its flags, inputs, outputs, and schema IDs. People, tools, and AI agents can inspect and wire up components without reading source.

Also built in

  • Schema versioning. Every event carries _schema and _nebu_version. A breaking output change gets a new schema ID, so consumers can detect the change instead of misreading the new output.
  • Archive throughput. Archive mode typically reads 100–500 ledgers/sec, depending on buffer size, network, and the archive you read from. See ARCHIVE_MODE.md.
  • Resumable fetch. Opt-in checkpoints let a bounded nebu fetch to a file resume from the last durable ledger. They cover the fetch itself, not the processors downstream of it.
  • Explicit status. Automation reads a stable nebu.status.v1 NDJSON stream of lifecycle and progress events. Terminals get OSC 7501.
  • Runtime hooks. Metrics, tracing, progress, and agent gates. See HOOKS.md.

Pipelines you can run

Replay the same ledgers through different processors

One fetch, many processors. Fetch a ledger range once, then run it through as many processors as you like. Extract transfers, scan contract events, or test new processing logic without requesting the same ledgers again. Each processor is its own program, not a plugin inside a runtime.

nebu fetch 60200000 60200100 > ledgers.xdr
cat ledgers.xdr | token-transfer | jq 'select(.transfer)'
cat ledgers.xdr | contract-events | grep -i swap

Backfill historical Stellar data

Read history from the public aws-public-blockchain S3 archive. You don't need an AWS account, and there are no RPC rate limits.

nebu fetch --mode archive \
  --datastore-type S3 \
  --bucket-path "aws-public-blockchain/v1.1/stellar/ledgers/pubnet" \
  --region us-east-2 \
  62080000 62080100 | gzip > historical.xdr.gz

Export USDC transfers to a file

Extract, filter, and store. The shell's pipe does all of the wiring.

token-transfer --start-ledger 60200000 --end-ledger 60200100 \
  | jq -c 'select(.transfer.assetCode == "USDC")' \
  | json-file-sink --out usdc.jsonl

One transaction can produce several legitimate transfer events (a path payment, for example), so don't deduplicate transfers by meta.txHash alone.

Send events to multiple destinations

One stream, many sinks: live NATS for consumers, a JSONL archive on disk, and a readable tail in the terminal.

token-transfer --start-ledger 60200000 \
  | tee >(nats-sink --subject "stellar.live" --jetstream) \
  | tee >(json-file-sink --out archive.jsonl) \
  | jq -r '"L\(.meta.ledgerSequence): \(.transfer.amount)"'

Query blockchain events with SQL

Run SQL aggregations directly over the stream. There's no database to set up and no ETL job to write.

token-transfer --start-ledger 60200000 --end-ledger 60200100 \
  | duckdb -c "
    SELECT json_extract_string(transfer,'\$.assetCode') AS asset,
           COUNT(*) AS n
    FROM read_json('/dev/stdin')
    WHERE transfer IS NOT NULL
    GROUP BY asset ORDER BY n DESC"

Connect to your own RPC provider

Point any origin at an authenticated RPC endpoint with NEBU_RPC_AUTH for higher throughput and private lanes.

export NEBU_RPC_AUTH="Api-Key YOUR_KEY"
token-transfer \
  --rpc-url https://rpc-pubnet.nodeswithobsrvr.co \
  --start-ledger 60200000 --end-ledger 60200100

See also nebu(1) › Examples for the full reference, and docs/DUCKDB_COOKBOOK.md for more SQL recipes.

Build once. Share with everyone.

An ecosystem of small, useful programs. nebu processors are independent executables. Build one to extract a new event type, decode a protocol, filter a stream, or send data to another service. Then publish it to the community registry so others can find it with nebu list, install it with nebu install, and combine it with their own tools.

You don't need to change nebu core to extend what people can build with it.

From a simple pipe to an operated pipeline

nebu

Build and compose

Explore ledgers, write processors, and connect them with Unix pipes on one machine.

flowctl

Run and supervise

Launch, wire, monitor, and restart pipelines made of several components.

Start with nebu for direct, lightweight composition. When you need supervised execution, flowctl can take over. nebu publishes a process contract (discovery through --describe-json, a status file, exit codes) for a supervisor to launch against. nebu itself never takes on orchestration.

Every processor is agent-legible

--describe-json emits flags, inputs, outputs, and schema IDs. Runtime hooks expose metrics, tracing, progress, and agent gates. The contract is small enough for an LLM to hold in its head.

nebu list
nebu describe token-transfer
token-transfer --describe-json | jq .
