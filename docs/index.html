Get started

Make Stellar data composable

nebu turns Stellar ledgers into streams of JSON that any program can read. Standalone processors extract and filter events; Unix pipes connect them to jq, DuckDB, Postgres, NATS, or your own code.

Start with a pipe. Add infrastructure when you need it.

35 published processors 5 documented schemas Contract stable since v0.5.0 
token-transfer --start-ledger 60200000 --end-ledger 60200100 \
  | jq -c 'select(.transfer.assetCode == "USDC")'

One processor, one pipe. Token transfers from a ledger range, narrowed with jq.

Install

go install github.com/withObsrvr/nebu/cmd/nebu@latest
export PATH="$HOME/go/bin:$PATH"
curl -sSL https://nebu.withobsrvr.com/install.sh | sh
docker run --rm withobsrvr/nebu:latest --version
docker run --rm withobsrvr/nebu:latest \
  fetch 60200000 60200001 > ledgers.xdr

The canonical path. Requires Go 1.22 or newer. Then run nebu install token-transfer.

Grabs a pre-built binary from the latest GitHub release. No Go toolchain required. Read the script before piping to sh if that's your policy.

What you can build

nebu doesn't ship an indexer. It gives you the parts.

Custom indexers

Extract the transfers, contract events, and invocations your application needs, and write them where you want: a JSONL file, Postgres, or a NATS subject.

Analytics

Pipe events into DuckDB and query them with SQL. There is no warehouse to stand up first.

Alerts and automations

Follow the chain live and hand matching events to a queue or a script.

Protocol-specific tools

Pair the generic origins with your own decoder to track one protocol, and publish it as a processor without touching nebu core.

How it works

Stellar provides the ledger data. nebu makes it easy to pipe.

nebu packages Stellar's supported indexing primitives (RPC-backed ledger access, the ingest SDK, XDR-native extraction) as standalone processor binaries behind a stable Go contract. Each processor does one job and speaks newline-delimited JSON on stdin and stdout.

Stellar RPC --mode rpc (default) Recent ledgers, live tail
GCS / S3 archive --mode archive Ledger history, bulk backfill
LedgerCloseMeta (XDR)
Origin token-transfer · contract-events · contract-invocation
typed events (JSON, _schema=nebu.*.v1)
Transform, or any stream tool usdc-filter · amount-filter · time-window · jq
filtered events (meta preserved)
Sink, or your own program json-file-sink · nats-sink · postgres-sink · duckdb · your code

Two ledger sources, one contract. Use --mode rpc for live tailing and recent ranges. Use --mode archive against a GCS or S3 ledger archive to read as far back as the archive holds, without RPC rate limits. The XDR, the processors and the JSON on the way out are the same.

Your pipeline, your tools. Processors are ordinary executables. Anything that reads a stream can sit next to them: jq, DuckDB, tee, or a program you wrote in another language.

Named after the Nebuchadnezzar from The Matrix: the vessel that carries data from on-chain truth to your applications.

Designed for composition

Compose with anything

Processors read stdin and write stdout. Put jq, DuckDB, tee, or your own program anywhere in the pipe. No daemon, no orchestrator, no pipeline file.

Two sources, same processors

Stream recent ledgers from RPC or read history from a GCS or S3 archive. Archive mode skips RPC rate limits, and the events that come out are identical.

Build and share processors

pkg/processor and pkg/source are committed-stable and checked in CI against API snapshots. Ship your processor as its own binary and register any Git repo with a description.yml.

Self-describing, for tools and agents

Every processor answers --describe-json with its flags, inputs, outputs, and schema IDs. A script or an agent can compose a pipeline without reading source.

Schema versioning

Every event carries _schema and _nebu_version. A breaking change bumps the schema version, so a query that filters on _schema keeps meaning what it meant.

Resumable fetch

Opt-in checkpoints resume bounded file backfills from the last durable ledger. Output is synchronized before checkpoint advancement, with range and path-alias validation built in.

Explicit status

OSC 7501 reports interactive state to terminals. Automation consumes the separate, stable nebu.status.v1 NDJSON lifecycle and progress stream.

Event format

Processors write newline-delimited JSON to stdout. Every event carries the nebu envelope alongside its payload data.

Cookbook

Replay the same ledgers through different processors

Fetch a ledger range once, then run the file through as many processors as you like. No repeated RPC calls.

nebu fetch 60200000 60200100 > ledgers.xdr
cat ledgers.xdr | token-transfer | jq 'select(.transfer)'
cat ledgers.xdr | contract-events | grep -i swap
Separate fetch from process nebu fetch passes raw LedgerCloseMeta XDR directly from RPC or archive storage to stdout, without a decode/re-encode cycle — capture a ledger range once and replay it through any number of processors. Great for backfills, regression tests, and comparing two schema versions over the same ledgers.

Filter and store USDC transfers

Extract, filter, store: three programs and two pipes.

token-transfer --start-ledger 60200000 --end-ledger 60200100 \
  | usdc-filter \
  | json-file-sink --out usdc.jsonl

Query events with SQL

DuckDB reads the stream from stdin. No database to set up, no schema to declare.

token-transfer --start-ledger 60200000 --end-ledger 60200100 \
  | duckdb -c "
    SELECT json_extract_string(transfer,'\$.assetCode') AS asset,
           COUNT(*) AS n
    FROM read_json('/dev/stdin')
    WHERE transfer IS NOT NULL
    GROUP BY asset ORDER BY n DESC"

Send one stream to several destinations

tee splits the stream: NATS for live consumers, a JSONL file on disk, a readable tail in the terminal.

token-transfer --start-ledger 60200000 \
  | tee >(nats-sink --subject "stellar.live" --jetstream) \
  | tee >(json-file-sink --out archive.jsonl) \
  | jq -r '"L\(.meta.ledgerSequence): \(.transfer.amount)"'

Backfill from the public archive

Read history from the public aws-public-blockchain S3 bucket. No AWS account, no RPC rate limits. Pubnet only.

nebu fetch --mode archive \
  --datastore-type S3 \
  --bucket-path "aws-public-blockchain/v1.1/stellar/ledgers/pubnet" \
  --region us-east-2 \
  62080000 62080100 | gzip > historical.xdr.gz

Use your own RPC provider

Set NEBU_RPC_AUTH and pass --rpc-url to use an authenticated endpoint.

export NEBU_RPC_AUTH="Api-Key YOUR_KEY"
token-transfer \
  --rpc-url https://rpc-pubnet.nodeswithobsrvr.co \
  --start-ledger 60200000 --end-ledger 60200100

See also nebu(1) › Examples for the exhaustive reference, and docs/DUCKDB_COOKBOOK.md for deeper SQL recipes.

Processors

Processors are independent executables. Build one to extract a new event type, decode a protocol, filter a stream, or write to another service. Publish it through the registry and anyone can nebu install it. You don't need to change nebu core to extend it.

nebu and flowctl

nebu is for building and composing: explore ledgers, write processors, connect programs with pipes. flowctl is for running and supervising: it starts a pipeline's components, monitors them, and keeps them running. Start with nebu. Move a pipeline to flowctl when it needs to be operated.

Aspect nebu flowctl
JobBuild and composeRun and supervise
Best forPrototyping, ad-hoc analysis, single-machine pipesPipelines that need to be operated and monitored
TopologyA shell pipe, with tee for fan-outDAG pipelines with fan-out and fan-in
Processor languagesGo SDK, or any language that implements the processor contractGo and JavaScript/TypeScript SDKs
Runs asProcesses you startComponents under a control plane

Every processor is agent-legible

--describe-json emits flags, inputs, outputs, and schema IDs. Runtime hooks expose metrics, tracing, progress, and agent gates. The contract is small enough for an LLM to hold in its head.

nebu list
nebu describe token-transfer
token-transfer --describe-json | jq .
